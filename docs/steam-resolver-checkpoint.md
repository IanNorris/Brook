# SteamRT resolver-file checkpoint

The socket repairs in `cd7f9914` pass 21 native Unix-name cases and 17 TCP/UDP
cases. Steam's own numeric probe then records successful Unix peer-name queries
and plausible accepted-TCP stream lengths, but the client still reaches its
Unexpected Transport Error dialog rather than login.

## A separate resolver defect

The outer guest resolves public Steam hostnames in roughly 20–40 ms using
`10.0.2.3`. The same unchanged SteamRT launch configuration reports no nameserver
line and `getent ahostsv4 store.steampowered.com` exits 2 after ten seconds.
This is evidence of a container resolver problem, not yet proof that it causes
the transport dialog.

An isolated native mount-namespace control identifies the filesystem mismatch:

- Normal `/etc/resolv.conf` reads and descriptor stat return 51 bytes.
- Metadata-only `O_PATH` open fails with `ENOENT`.
- Binding that source onto a scratch file also fails with `ENOENT`.
- Copying the generated bytes into a real scratch file makes its bind succeed;
  the bound bytes match and contain one nameserver line.

The historical resolver exists only in the syscall's synthetic-file fallback.
VFS object lookup, retained descriptors and bind mounts cannot retain it.
Container roots intentionally disable pathname-based synthetic fallback. That
namespace rule must remain intact.

The candidate puts a real resolver seed in the RAM-backed initrd, updates the
existing file after boot-time DHCP/static configuration, and removes the
synthetic open/stat/access exceptions for that path. Native `resolver_file_check.py
--bind` verifies content, read/stat/O_PATH identity and direct bind behavior.
The production build, all 104 host tests and both existing compiled entry and
scheduler-start audits pass. Linux passes the ordinary file-identity control.
DNS refresh after boot is outside this change.

The identical SteamRT resolver control now prints `nameserver=10.0.2.3` and
returns lookup exit 0 within the measured second, compared with exit 2 after ten
seconds before the repair. The complete runtime job exits 0 with all tasks
drained and both streams at EOF. This verifies the runtime DNS repair; full
Steam login remains a separate acceptance gate.

The full retry still reaches Unexpected Transport Error. Its network helper
now records successful non-loopback receives, while the sampled main process
records 767 successful Unix peer-name queries. A two-second profile captures
1,594 CPU samples and 11,619 context switches without reported drops; sampled
execution is predominantly idle. This supports investigating waits rather than
CPU saturation, subject to the profiler's IRQ-masked sampling limitation.
The run drains all tracked groups, restores its wrapper, passes heap integrity
and checked sync, and exits through the original QEMU owner with all four
offline filesystem checks clean.

## Preserved failure evidence

The earlier full Steam run eventually double-faults below PID 122's kernel
stack. The saved stack contains many repeated scheduler-lock and LAPIC timer
return addresses. The lock timeout diagnostic enables interrupts before panic;
Astra's source review confirms that this can permit recursive timer entry while
waiting for the scheduler ticket. It does not identify the initiating lock
stall. The timeout path now leaves interrupts disabled. Serial output polls the
UART, but still has its own lock dependency; reliable panic delivery and the
original lock stall are not claimed fixed.

`scripts/audit_scheduler_lock_wait.py` inspects every emitted ticket-wait body,
rejects interrupt-restoring instructions and fails if no body is found. It
rejects the preserved old kernel's `STI`; the rebuilt kernel passes, as do
inserted-STI and missing-body rejection mutations and both existing compiled
entry/scheduler-start audits. This is a focused compiled property check, not a
general scheduler-safety proof or a live forced-deadlock acceptance test.

That halted VM's registers, bounded kernel stack, logs and private disks are
preserved. No clean sync was possible. Post-stop checks report errors on its
data/tmp filesystems and clean nix/boot filesystems; it is not a test baseline.
The subsequent isolated resolver-control VM completes checked sync, original
owner exit and all four offline filesystem checks successfully. New candidates
start from the earlier checked baseline, not the failed disks.


## FD-diagnostic lock stall

A later full-client run panics on a scheduler-lock timeout in
`ReleaseSchedulerReference`. The saved NMI state places CPU 1 in
`SchedulerGetFdInfo` while the other active CPUs wait for scheduler locks.
Its compiled instruction address is the FD ticket-lock wait, inside the
process-list critical section. This exposes a lock dependency: a preempted
FD-lock owner may need the process-list lock during post-switch reference
release before it can resume and release the FD lock. This is a concrete
unsafe dependency; the capture does not identify the original FD-lock owner.

FD lookup and enumeration now use a nonblocking FD-lock attempt while holding
the process-list lock. On contention they release the process-list lock and
yield, then repeat the PID/incarnation lookup. No borrowed process or FD pointer
is dereferenced after dropping the registry lock. Snapshot copying remains
under both locks, preserving the existing lookup and incarnation semantics.

The hosted regression includes the actual implementation and deterministically
requires scheduler work to resume the FD-lock owner. Both lookup and enumeration
complete after contention; process removal, PID reuse, termination, invalid FDs,
and empty enumeration are also checked. The exact old implementation times out
in this regression. All 105 host tests pass, the production kernel builds, and
entry, scheduler-start and lock-timeout compiled audits pass. The Linux control
and an eight-CPU native run each complete 4,000 shared-FD churn iterations and
2,000 proc FD snapshot iterations. The native command exits zero with no live
tasks and both output streams drained. This focused test does not prove general
scheduler deadlock freedom or resolve the intermittent red-bar rendering issue.

The failed full-client run's registers, bounded stack pages, logs, kernel and
private disks are preserved. It could not sync; offline checks report errors on
data/tmp and clean nix/boot filesystems. Validation uses fresh checked copies,
not those failed disks.

Before that panic, the transport probe observed actual helper requests being
answered with HTTP 403 by the main Steam process. Own wrong-route GET controls
on one listener produce HTTP 404 instead; the other listener produces no response
within the bounded read. This narrows the next investigation to the actual
request/rejection metadata. It does not yet establish an authentication-policy
or socket-owner-lookup cause. Steam login remains unverified.

The validation VM subsequently passes heap integrity, checked guest sync, original
owner exit zero, and all four offline filesystem checks. Astra's read-only
review finds no introduced blocker in the retry repair. It separately identifies
an existing exec-publication race and incarnation-zero teardown caveat, recorded
in the backlog; this change does not claim to fix those lifetime boundaries.


## Genuine WebSocket request comparison

A private bounded classifier now inspects at most the first 4 KiB of each
successful loopback transfer. It exports fixed enums, booleans and status codes,
never request paths, header values, payloads or authentication material. It does
not reconstruct streams: complete-header flags apply only to the captured call.
Synthetic complete/partial headers and rejection categories pass, as does the
native byte-preservation/error control. Unsupported TCP shutdown remains an
explicitly reported gap, not a successful acceptance case.

In the repaired Brook kernel run, the helper sends complete HTTP/1.1 GET
requests to localhost with a Host port matching the receiving listener. Both
sides observe Upgrade/Connection WebSocket headers, a WebSocket key and version
13, an Origin differing from Host, and no Authorization or Cookie header. The
main process sends HTTP 403, and the helper receives it. Eighteen paired
rejections are recorded without malformed classification rows or hitting its
output cap. The fixed rejection-term classifier finds no matching body reason.
The UI capture at the earlier observation is a black Xwayland surface, not a
verified login screen.

An isolated Linux VM with a fresh private home and the same classifier sends the
same broad request categories but receives HTTP 101 for both connections. Its
VM-only screenshot verifies the QR login UI. This supports treating the
Host/Origin difference as normal for this client; it does not establish exact
request equivalence. Duplicate headers, Origin scheme/authority, WebSocket key
validity, subprotocol and route remain acceptance-relevant blind spots.

Whole Steam executable files differ between the two prepared environments.
Boolean-only offline comparisons establish identical `.text`, `.rodata` and
`.data` sections in the main executable, both present steamclient.so copies,
and steamrt64/steamui.so. This is consistent with environment-specific ELF
patching; it is not a claim that every loaded library or runtime configuration
is identical. No executable hashes or contents are included in this checkpoint.

A subsequent whole-startup Linux syscall trace is disturbed by the preload's
own raw metadata calls and does not reproduce a new genuine handshake. It is
retained as a limited diagnostic and is not used to infer absent application
checks. The next comparison should isolate application-issued metadata queries
or capture module-relative callers at the server's 403 versus 101 send, while
refining request validity flags. Missing INET socket options or incomplete
socket-owner procfs data are not promoted to causes without those observations.

Both experiments restore their original helper wrappers and complete checked
sync and original-owner exit zero. Brook's four offline filesystem checks and
the Linux read-only filesystem check pass. Steam login on Brook remains
unverified; the Linux login screen is a reference only.

## Socket discovery repair

Application-only metadata probes identify repeated `lsof` children. Across 47
matched invocations they observe 91,433 successful proc FD readlinks, none using
the Linux socket identity syntax. A separate owned-listener control confirms
that Brook reports inode zero, a generic FD label, and no matching TCP row.
The Linux control passes those checks and finds its listener with `lsof`.
These are positive compatibility failures, not proof that every 403 has the same
cause. Interposition misses internal libc/raw syscalls, successful path calls
are the recorded subset, and individual process logs have explicit caps.

INET sockets now receive monotonic, non-reused inode identities independent of
PID, FD number and reusable socket slot. Fully initialized descriptors cache
their `socket:[inode]` label before publication; aliases retain it. A short
registry guard protects slot reservation/publication/retirement and scalar proc
snapshots, with allocation, transmission and close waits outside the guard.
The guard prevents cross-lifetime identity mixing; mutable connection tuple and
state writers are not all synchronized by this guard.

`fstat`, followed proc FD metadata, and TCP/UDP rows agree on identity. Ports
are formatted in host byte order and Linux UID/inode columns are present.
Accepted ownership uses the accepting task's credentials captured before its
blocking wait. Matched modules use ABI 52.

Following a socket yields a metadata-only object: ordinary opening returns
`ENXIO`, while `O_PATH` retains immutable identity after socket close/reuse.
Same-owner foreign-process inspection is necessary for `lsof`. Its bounded
policy checks canonical credentials, namespace and capabilities while copying
the protected socket metadata. A busy FD lock causes both snapshots to retry
after releasing credentials; the exact acquired lock is released. This does
not grant process memory access, directory traversal, or reopening another
process's socket. It does not implement general Linux ptrace/dumpability policy
or repair the separately recorded exec/FD-table publication race.

Regression coverage includes concurrent inode allocation/exhaustion, label
bounds and constant initialization; the actual credential/FD snapshot body
under contention and ownership changes; and native TCP/UDP, aliases, accepted
ownership, cross-process permission checks, retained `O_PATH`, and 800 socket
lifetimes across eight workers. A failed early boot exposed a dynamic C++
initializer dependency; it is corrected with constant initialization and its
private evidence is preserved. Native tests use fresh checked disk copies.

SteamRT's actual `lsof` finds the owned control listener. Genuine main-client
responses in the first full-client run continue to return 403, and the captured
desktop remains black. Endpoint correlation identifies the recorded 101 as
synthetic probe-control traffic, not a successful client handshake; it must not
be counted toward login acceptance. Both endpoint-specific rejection and
rendering remain open. That run restores its helper wrapper, passes heap/sync
checks, exits its original VM owner zero, and passes all four offline filesystem
checks. No proprietary files, request payloads, executable hashes or credentials
are included in this checkpoint.

The final atomic-snapshot kernel repeats all native identity, ownership, actual
SteamRT lsof, and probe controls successfully, then completes heap integrity,
checked sync, original-owner exit zero and all four offline filesystem checks.
Its genuine main-client trace contains 22 HTTP 403 responses across both local
listeners and no successful main-client upgrade in that capture. Synthetic
probe records are excluded by executable-qualified application PID. The host
suite passes 106 of 107 tests in the concurrent run; its existing FD stress test
is explicitly stopped after excessive host contention, then passes alone in
0.65 seconds. Both new tests pass, as do the three compiled entry/scheduler
audits. Login remains unverified; next compare the request/rejection paths
without attributing synthetic control responses to Steam.
